# Feature selection and scope control

## Candidate set

Evaluate options against the same observed problem. Do not score unrelated features merely to create a roadmap ranking.

| Option | Smallest useful scope | Existing reuse | Principal dependency |
| --- | --- | --- | --- |
| Improve recipes | Fix one proven discovery, clarity or print problem | Current catalog, filters and print styles | Correct diagnosis of the bottleneck |
| Organise saved recipes | One simple organisation workflow if bookmarking is insufficient | Existing saved records and verified identity | Compatibility with native saves |
| Weekly recipe planner | Assign accessible recipes to days and print a weekly list | Recipe IDs, access checks, cards and account shell | New persistence only after inventory confirms the gap |
| Reviewed feeding resources | A small reviewed answer to a repeated content question | Native article structures and editorial workflow | Rights, freshness and subject review |
| Another recipe collection | One new fixed release with a clear offer | Catalog, release membership and commerce | Commercial approval and payment remediation |
| Child profiles or milestones | A separate scoped proposal | Native profile/milestone source | Child-data lifecycle, ownership and expert content review |
| AI assistant | A separate bounded proposal | Native chat ideas only after security redesign | Demand, evaluation, provider privacy, limits and recurring cost |
| Hold | Continue recipe operations and gather evidence | Current product | Named follow-up question and review date |

Hold is not failure. A reliable small product is a valid outcome. Recipe optimisation belongs to a named maintenance change with its own acceptance criteria, not an excuse to skip evidence.

## Hard filters before scoring

Reject or defer any option without a defined customer problem, owner, feasible data boundary, compatible existing rights or bounded operating cost. Stop options depending on unreviewed child records, privileged client keys, unresolved cross-user access or broad medical claims. High demand does not override these requirements.

Do not port a native screen merely because the code exists. Do not add a database, CMS, subscription system or AI vendor until a selected scope needs the dependency and existing tools fail the requirement.

## Scoring proposal

Score 0–4 using linked evidence. Weights sum to 100. Calculate weighted score as `sum(weight * score / 4)`. Missing evidence is marked unknown and blocks a final recommendation, rather than receiving a favourable estimate.

| Dimension | Weight | Score 0 | Score 4 |
| --- | --- | --- | --- |
| Recurring customer problem | 30 | No observed problem | Repeated recent examples across sources |
| Connection to recipe use | 20 | Separate audience and job | Direct next step in current recipe workflow |
| Validated usefulness | 15 | No task evidence | Prototype helps users complete the named task |
| Delivery confidence | 15 | Major unknown dependencies | Existing contracts and bounded implementation |
| Privacy/support simplicity | 10 | Sensitive data and unresolved operations | Minimal data, clear ownership and recovery |
| Sustainable cost | 10 | Unbounded or unowned cost | Measured estimate within an approved ceiling |

Report confidence separately from score. Scores are decision aids, not proof of market demand. Include expected engineering days as a range and explicit assumptions. Do not subtract safety risk into an average score which conceals a blocking defect.

## Decision sequence

1. Review the Phase 11 operating record. Repair access, payment or content issues first.
2. Compare two or three interventions for the same problem, including improving the current experience.
3. Run one prototype task per candidate. Use synthetic recipes or content users already have permission to view.
4. Record task completion, confusion, objections and accessibility issues.
5. Select one slice, choose hold, or name the missing evidence and research limit.
6. Approve a one-page feature charter and required acceptance scenarios before code changes.

## Feature charter

The charter records problem ID, target segment, user outcome, included behaviours, explicit exclusions, routes, source reuse, data classes, access rule, commercial terms, experiment duration, primary metric, stop conditions, cost ceiling, owner and evidence links.

For the planner proposal, the scope is one private weekly list with one recipe per day, no child profile and no generated meal advice. Grocery aggregation, nutrition totals, portions, drag-and-drop, reminders, sharing and offline sync remain excluded. A requested extension enters the change log with impact on evidence, privacy, testing and cost.

## Alternative branch requirements

If recipe discovery wins, identify the failing query/filter/content pattern, preserve free-versus-paid boundaries, and compare completion of the same finding task before and after. Avoid adding filters whose catalog tags are incomplete.

If saved organisation wins, extend existing bookmark semantics with an additive relationship. Do not replace saved IDs or require a recipe purchase to remove an inaccessible bookmark. Define organisation ownership, deletion and cross-device conflicts before building.

If resources win, reuse source articles only after rights and editorial review. Define author/reviewer, revision, publication state, withdrawal and public-versus-paid access. Use public educational copy, not imported personal tips. Reopening `/resources` requires a deliberate proxy, navigation, metadata and sitemap change with tests. Do not resurrect the whole legacy page.

If another collection wins, use a new approved release and the Phase 5/8 publishing and commerce gates. Never mutate a sealed purchased manifest to imply a new entitlement or change historical pricing. This branch needs a collection-specific charter and acceptance addendum before implementation.

The detailed planner contract is not a universal specification for these alternatives. Replace the planner-specific task scope and scenario mapping with an approved addendum before selecting another build branch. Retain common research, rights, security, measurement and rollout gates.
